# 변경 기록

모든 버전은 Git 태그로 남아 있다. 특정 버전을 보려면 `git checkout v0.1.0`을 실행한다.

## v1.3.0 (2026-11-26, 로컬) — GitHub Action 전환
- **LLM 연결 방식 추가:** OpenAI 형식 `/chat/completions`를 부르는 `OpenAiCompatibleClient`. `SR_LLM_PROVIDER=openai`로 켠다. OpenAI, Groq, Ollama `/v1` 모두 연결된다 (README)
- **PR 헝크 검토 API `POST /internal/review-hunk`** (`HunkReviewService`, `docs/TEAM_API.md`): 헝크에 걸린 경고를 기존 판정 로직으로 판정한다. 시간은 경고 한 건 30초에서 **PR 전체 예산(최대 45초)**으로 바꿨다. 진짜 취약점에는 남은 시간으로 설명과 수정 방향을 만든다
- **상수 판정 수정:** 같은 파일의 `final` 필드(`private static final String TABLE = "users"`)를 상수로 계산하지 못해 LLM에 넘기던 문제
- 측정 (GitHub 기본 러너, 판정 1건): Groq `openai/gpt-oss-120b` 1~2초, `qwen/qwen3.8-27b` 1~1.4초. 같은 러너의 Ollama 7B 72초, 3B 53초는 30초 제한을 넘음
- **사용 한도(429) 처리:** 전에는 한도에 걸리면 기다리지 않고 바로 다시 보내 결국 판정 불가가 됐다. 이제 API가 알려 준 시간만큼 기다렸다 다시 보내고(시도 횟수에 넣지 않음, 최대 3번), 하루 한도처럼 1분 넘게 기다려야 하면 바로 "사용 한도" 판정 불가로 둔다. 응답의 `rateLimited`로 PR 요약에 "사용 한도에 걸렸다"고 알린다. 429 본문(조직 ID 포함)은 로그에 남기지 않는다
- **외부 API 측정기** (`ApiBench`, runner-bench `groq-bench` 워크플로): OWASP Benchmark SQL·명령어·경로·XSS에서 진짜·안전을 같은 수로 504건 골라 PR 검토와 같은 순서로 판정. 무료 하루 한도를 넘으므로 결과를 한 건씩 저장하고 이어서 잰다. 사용 토큰도 센다
- 실제 PR 확인 (asdf1454/secureview-runner-bench PR 1): SpotBugs+FindSecBugs SARIF → 판정 → 댓글. SQL 인젝션은 진짜 취약점으로 댓글, 허용 목록으로 정렬 열을 고르는 SQL은 오탐 추정. PR 검토 단계 5~8초

## v1.2.0 (2026-11-18, 로컬)
- **상수 판정 (`ConstantArgs`):** 위험한 호출(SQL 실행, `Runtime.exec`·`ProcessBuilder`, `File`·`FileInputStream`·`Paths.get`, 응답 `print`·`write`·`format`)에 들어가는 값이 공격자가 바꿀 수 없는 값뿐인 것을 코드로 계산할 수 있으면, LLM을 부르지 않고 오탐 추정으로 판정 (`JudgeService`, CWE-89·78·22·79)
  - 결과가 정해지는 if·switch는 실행되는 쪽만 보고, List·Map은 넣고 뺀 순서를 따라가고, 같은 파일의 도우미 메서드·내부 클래스 메서드도 따라감
  - 상수 외에 믿는 값은 두 가지: `System.getProperty("...")`, 대문자 이름 필드(`Utils.TESTFILES_DIR` 같은 상수 관례). **가정이므로 실제 코드에서 틀릴 수 있음**
  - 모르는 값(매개변수, 소문자 필드, 다른 파일의 메서드, 다른 코드가 바꿀 수 있는 StringBuilder·배열·List)이 섞이면 판정하지 않고 LLM에 넘김
  - break·continue, try·catch, 화살표 case, 람다, 같은 객체를 가리키는 두 이름도 따라가거나 판정을 포기함 (각각 테스트로 확인)
  - OWASP Benchmark (FindSecBugs 경고가 있는 테스트, LLM 없음): 안전 경고를 SQL 173/232, XSS 106/147, 경로 조작 69/135, 명령어 삽입 18/125 거름. **진짜는 네 분류 모두 0건 거름.** 직접 만든 예제의 진짜 취약점도 0건
  - 측정: `docs/benchmark-constant.mjs`와 `ConstantArgsBench` (LLM 없이 몇 초). 결과 원본 `tools/bench-results/constant-args-2026-11-18.txt`
- **근거 검사:** SQL 경고에서 LLM이 SQL을 막지 못하는 처리(HTML 인코딩, 입력을 이어 붙인 쿼리의 `?` 바인딩)를 "안전 처리"로 대면 판정 불가로 바꿈. Benchmark 표본에서 진짜를 지운 3건이 모두 이 경우였음
- 수정안 API `POST /internal/fix` (11/13, `FixApiService`). 명세에 없는 경로라 팀 확인 필요
- 표본 30건 기준 추정 (기록된 LLM 응답에 적용): 오탐 감소 2/15 → 11/15, 재현율 12/15 → 15/15. **LLM으로 다시 재지 않음** (팀 GPU PC에서 잴 예정)
