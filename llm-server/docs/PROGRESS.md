## 4. 처리 시간

![단계별 처리 시간](charts/time-by-step.svg)

| 항목 | 시간 | 근거 |
|---|---|---|
| 500줄, 경고 5건, S4~S5, 설명 제외 | 중앙값 40.1초 (36.4~40.5초), 제한 40초 | 단독 10회 측정, `docs/eval/v1.1.2-speed-500lines-rerun.txt` |
| API, 진짜 취약점 1건 (판정+설명) | 중앙값 19.1초 (17.2~24.4초) | 17회 측정, 모두 설명 포함 |
| API, 오탐 추정 1건 | 7.2~9.6초 | 9회 측정 |
| 판정 1건 | 약 7.6초 | v1.1.0에서 5건을 모두 판정한 7회의 평균 약 38.2초를 5건으로 나눈 값 |
| 수정안 1건 | 중앙값 12.1초 (5.7~34.9초) | 21건 |
| 질의응답 1건 | 2.4~10.3초 | 질문 4개 |
| 모델 올리기 | 약 18초 | 서버 시작 때 1회 |

수정안과 질의응답 시간은 v1.0.3 측정값이다. v1.1.0에서 이 프롬프트는 바꾸지 않았고, 다시 재지 않았다.

- **속도가 빨라진 이유:** 처음에는 판정과 설명을 함께 만들어 건당 28~34초가 걸렸다. 판정을 먼저 끝내고 설명을 리포트 뒤로 미뤘다.
- **시간 제한의 효과:** v1.0.3부터 진행 중인 호출도 제한 시간에 끊는다. 제한 40초에서 10회 중 7회는 5번째 경고가 판정 불가로 남았다(v1.1.0은 3회, v1.0.3은 6회). 평가 직후 측정에서는 10회 모두 남았다. v0.9.0은 같은 측정에서 끊지 않아 42.9초였고 5건을 모두 판정했다.
- **API의 전체 시간:** API는 경고마다 판정과 설명을 함께 돌려준다. 이 PC에서 진짜 취약점 5건이면 약 1분 40초라 1분 목표를 넘는다. 팀 GPU PC에서 다시 재야 한다.
- **남은 시간:** 제한이 40초면 S0~S3과 화면 표시에 약 20초가 남는다. 이 시간이 충분한지는 아직 모른다.
- **경고가 많을 때 (Java 묶음 판정):** 제한 시간까지 심각도 순서로 판정하고, 나머지는 판정 불가로 남긴다. 경고를 지우지는 않지만 그 경고의 오탐은 줄지 않는다.
- **측정 PC:** RTX 2050 4GB, RAM 16GB. 다른 PC에서는 시간이 달라진다.

"직접 읽은 결과"는 사람이 읽고 판단한 값이다. 컴파일과 재분석은 S7을 연결해야 할 수 있다.

**남은 문제 예시:**
- 포인터에 `sizeof(out)`을 사용해 복사 길이가 잘못됨
- `unsigned int` 덧셈을 `SIZE_MAX`로 검사해 오버플로를 막지 못함
- 위험한 코드를 사실상 실행되지 않게 만들어 기능이 달라짐
- 사용자 입력을 기준 폴더로 삼아 경로 검사의 의미가 약함

- 평가 22분 분량의 출력이 명령 실수로 저장되지 않아 다시 실행했다.
- 500줄 예제 주석 때문에 경고가 1건 더 잡혀 처음 속도 측정은 버리고 다시 쟀다.
- v1.0.3 재평가 때 다른 세션이 같은 폴더에서 같은 평가를 돌려 기록 파일이 섞였다. 속도·수정안·질의응답은 단독으로 다시 쟀고, 판정 평가는 정답 합계만 쓰고 시간 값은 쓰지 않았다.

## 8. 교수님 피드백 대응

| 피드백 | 현재 상태 |
|---|---|
| 처리시간이 러프함 | 단계별로 측정해 정리함 |
| Qwen 온라인 제공 여부 | 온라인 제공 없음. 서버 PC의 Ollama만 호출 |
| 구현 디테일 부족 | 코드, 테스트, `docs/TEAM_API.md`로 정리함 |
| 차별점 | 사실은 LLM이, 판정은 규칙이 맡는 구조로 설명 가능. 교수님 기대에 맞는지는 미확인 |
| 리얼타임, 코딩 중 도움 | **구현하지 않음.** 설명서 범위대로 진행. 판정 1건이 약 8초라 키 입력마다 판정하기는 어려움 |
| 코딩하며 불편했던 점 | **비워 둠.** 직접 경험을 적어야 함 |
