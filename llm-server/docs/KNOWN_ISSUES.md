# 알려진 문제 (v1.2.0, 로컬)

아래는 남은 문제입니다. API 명세와 다르게 동작하는 부분은 `TEAM_API.md`에 있습니다.

## 남은 문제

| 문제 | 재현 결과 | 영향 |
|---|---|---|
| 공식 평가에서 LLM만으로는 목표 미달 | OWASP Benchmark SQL 표본 30건: 오탐 감소 2/15, 재현율 12/15 (11/16) | v1.2.0의 상수 추적·근거 검사로 기록 기준 11/15, 15/15. LLM으로 다시 재야 함 |
| 상수 판정은 Java의 CWE-89·78·22·79만 | C 코드와 조건형 CWE(798, 120 등)는 LLM만 판정 | C는 파서가 없어 별도 작업 |
| 명령어 삽입은 14%만 거름 | 놓친 107건 중 95건이 다른 파일의 `Utils.getOSCommandString(...)`을 거침 | 다른 파일을 봐야 함 |
| 다른 파일을 봐야 하는 오탐 | `ThingInterface`, `SeparateClassRequest`, `Utils`의 메서드 | 업로드가 파일 하나라 불가능. 여러 파일 업로드는 12월 범위 |
| 믿는 값 가정 | `System.getProperty`와 대문자 이름 필드는 공격자가 못 바꾼다고 봄 | 대문자 필드에 요청 값을 넣는 코드라면 진짜를 놓침. Benchmark·예제에서는 0건 |
| 상수 추적으로 판정해도 `llm.model`에 모델 이름이 나감 | 명세 형식 B에 "규칙으로 판정"을 나타낼 칸이 없음 | `explanation`에 "LLM 없이 코드로 계산한 판정"이라고 적음. 팀과 표기 방법 확인 필요 |
| 질의응답이 관련 없는 질문을 그대로 되풀이 | "오늘 점심 뭐 먹을까요?"에 같은 문장으로 답함 | 안내 문구 없이 엉뚱한 답이 나옴 |
| 질의응답의 줄 번호 | 코드 범위 밖 번호는 다시 요청하지만, 범위 안의 틀린 번호는 잡지 못함. 수정 코드 예시에 16~18번 줄 번호를 붙임 | 사용자를 헷갈리게 함 |
| API 설명이 30초에 걸릴 수 있음 | 이번 17회는 모두 30초 안(최대 24.4초). v1.1.1 이전 측정은 18회 중 3회 초과 | 길거나 C인 함수, 느린 PC에서는 공격 예시 없이 판정 근거만 보일 수 있음 |
| API 전체 시간 | 이 PC에서 진짜 취약점 5건이면 약 1분 40초 (1건 중앙값 19.1초) | 1분 목표를 넘음. 팀 GPU PC에서 다시 재야 함 |
| 500줄 측정에서 시간 제한에 걸림 (Java 묶음 판정) | 제한 40초에서 10회 중 7회가 5번째 경고를 판정 불가로 남김 (v1.1.0은 3회) | 제한은 지키지만 그 경고의 오탐은 줄지 않음 |
| 질의응답 API 없음 | 명세에 주소가 없어 화면에서 호출할 수 없음 | 데모 포함 여부를 강민재 님과 정해야 함 |
| 수정안, 질의응답은 스키마 미적용 | 명세의 스키마 규칙은 판정(S5)에 적용. S6, S8은 `format: json` | S6는 12월 범위. 재측정하지 않음 |
| C 파일의 `function.name` | C 함수 이름을 찾지 않아 `(함수 없음)` | 데모는 Java라 영향 없음. 12월 전에 수정 필요 |
| 수정안의 실제 품질 | 코드를 읽어 보면 21건 중 약 16건만 제대로 고침 | 아래 "수정안" 참고 |

**수정안에서 확인한 문제:**
- CWE-79 1건은 사전 검사를 통과하는 수정안을 끝내 만들지 못함
- `sizeof(out)`을 포인터에 사용 (CWE-134)
- `unsigned int` 덧셈을 `SIZE_MAX`로 검사해 오버플로를 막지 못함 (CWE-190)
- 포인터에 NULL을 넣어 위험 코드를 실행되지 않게 만듦 (CWE-416)
- 사용자 입력을 기준 폴더로 사용 (CWE-22)

## 코드 수정만으로 해결되지 않는 것

- CWE-798, 120, 416, 476은 이번 측정에서 오탐을 줄이지 못했습니다 (각 0/2). 공식 평가 데이터로 개선해야 합니다.
- 수정안의 컴파일과 경고 해소는 S7을 연결해야 확인할 수 있습니다.
- 직접 만든 예제의 판정 수치(오탐 감소 12/23, 재현율 25/25)는 공식 평가가 아닙니다. 공식 수치는 `Desktop\SecuReview-LLM\SecuReview_공식평가_결과.md`에 있습니다.
- Benchmark의 안전 사례는 일부러 만든 패턴이라, 상수 추적이 실제 프로젝트에서 같은 비율로 걸러낸다는 뜻은 아닙니다. 실제 오픈소스 코드로 따로 재야 합니다.
- 실제 SpotBugs와 웹 서버를 붙여 실행한 것은 로컬 통합본(`local/integration`)에서만입니다 (v1.1.3). 팀 저장소의 main에서는 아직 연결해 보지 않았습니다.
- VPN(Tailscale) 환경과 HTTPS 없는 내부 통신은 시험하지 않았습니다.
- Ubuntu에서 테스트와 서버를 실행해 보지 않았습니다. 이 PC의 WSL은 Ubuntu 26.04이고 JDK가 없어, `./mvnw` 실행 권한만 확인했습니다.
- GPU PC에서 WSL2로 LLM 서버를 돌리고 Ollama를 Windows에 두면, WSL 안에서 `localhost:11434`로 Windows의 Ollama에 닿지 않을 수 있습니다. 이때는 `OLLAMA_URL`을 Windows 주소로 설정해야 합니다.
- 처리 시간은 RTX 2050 4GB 기준이며, S0~S3 시간은 측정하지 않았습니다.
