# SecuReview LLM 계층 결과 정리 (유환민)

1차 결과보고서와 12월 초 발표의 LLM 파트 원고입니다. 측정일 2026-11-09, 모듈 버전 v1.1.2.

## 1. 맡은 범위

| 단계 | 내용 | 상태 |
|---|---|---|
| S4 컨텍스트 추출 | Java는 JavaParser, C는 중괄호 스캐너로 함수 전체 추출. 150줄 초과나 판단 불가면 경고 라인 ±30줄 | 구현 |
| S5 판정·설명 | 진짜 취약점 / 오탐 추정 / 판정 불가, 근거 라인, 설명, 공격 예시 | 구현 |
| S6 수정안 | 진짜 취약점 함수를 안전한 코드로 재작성, S7 실패 이유를 받아 재생성 | 구현, S7 연동 전 |
| S8 질의응답 | 선택한 경고에 대한 자연어 질문 응답 | 모듈 구현, 화면 연동 전 |
| 모델 선정 | 3개 모델 비교 후 `qwen2.5-coder:7b` 선택 | 완료 |

## 2. 구현 방식

**LLM은 사실만 답하고, 판정은 코드 규칙이 내립니다.** 7B 모델은 사실을 맞게 답하고도 결론에서 모순된 답을 내는 경우가 있었기 때문입니다.

| CWE 유형 | 해당 CWE | LLM에게 묻는 사실 |
|---|---|---|
| 입력 흐름형 | 89, 79, 78, 22 | 외부 입력이 닿는가, 안전 처리를 거치는가 |
| 조건형 | 798, 120, 416, 476, 190, 134 | 위험 조건이 있는가, 막는 코드가 있는가 |

- **상호 검증:** LLM은 정적 분석이 찾은 위치에서만 판단하며, 경고를 지울 수 없습니다.
- **실패 처리:** 형식 오류, 범위 밖 근거 라인, 생성 실패는 한 번 다시 요청하고, 그래도 실패하면 판정 불가로 처리합니다. Ollama 연결 실패는 그 이유를 그대로 표시합니다.
- **동시 사용:** 8스레드 400회 함수 추출에서 오류가 없습니다. 서버에 연결한 전체 동시 사용은 아직 시험하지 않았습니다.
- **수정안 사전 검사:** 라인 번호, 문법, 함수 개수, 선언 유지를 확인합니다. 컴파일과 경고 해소 확인은 S7이 맡습니다.
- **속도 구조:** Java 묶음 판정은 판정을 먼저 끝내고 설명을 뒤에 채웁니다. API는 명세대로 한 응답에 함께 돌려주며, 설명만 30초를 넘으면 판정을 유지합니다.
- **출력 형식 강제:** 판정과 설명은 Ollama `format`에 JSON 스키마를 넣어 받습니다.
- **프롬프트 인젝션 방어:** 코드는 구분자로 감싸고, 그 안의 지시를 따르지 말라는 규칙은 시스템 프롬프트로 전달합니다.

## 3. 측정 결과

측정 환경: RTX 2050 4GB, RAM 16GB, Ollama 0.35.1, `qwen2.5-coder:7b`, 입력 한도 8192토큰.

### 판정 품질 (직접 만든 정답 예제 48건, CWE 10종)

| 항목 | 결과 | 목표 |
|---|---|---|
| 정답 | 37/48 | 없음 |
| 오탐 감소 | 12/23 (52%) | 30% 이상 |
| 재현율 | 25/25 (100%) | 하락 5%p 이내 |
| 판정 불가 | 0건 | 없음 |
| 프롬프트 인젝션 방어 | 4/4 | 없음 |

**이 수치는 공식 평가가 아닙니다.** 프롬프트를 고치는 데 사용한 예제로 잰 값이라 실제보다 좋게 나올 수 있습니다. 공식 수치는 OWASP Benchmark와 Juliet으로 다시 측정해야 합니다.

CWE-798·120·416·476은 이번 측정에서 오탐 감소가 0/2로, 약한 유형입니다. CWE별 결과는 실행마다 달라집니다 (예: CWE-476 0/2 → 1/2 → 0/2).

### 처리 시간

| 항목 | 시간 |
|---|---|
| 500줄 파일, 경고 5건, S4~S5, 설명 제외 | 중앙값 40.1초 (10회, 범위 36.4~40.5초, 제한 40초) |
| API, 진짜 취약점 1건 (판정+설명) | 중앙값 19.1초 (17회, 범위 17.2~24.4초, 제한 30초) |
| API, 오탐 추정 1건 | 7.2~9.6초 (9회) |
| 판정 1건 (설명 제외) | 약 8초 |
| 수정안 1건 | 중앙값 약 12초 (5.7~34.9초) |
| 질의응답 1건 | 2.4~10.3초 |
| 모델 올리기 | 약 18초, 서버 시작 때 1회 |

S4~S5를 40초로 제한하면 S0~S3과 화면 표시에 약 20초를 쓸 수 있습니다. 대신 10회 중 7회는 5번째 경고가 판정 불가로 남았습니다. S0~S3은 아직 측정하지 않았습니다. API는 경고마다 설명까지 함께 돌려주므로 이 PC에서 진짜 취약점 5건이면 약 1분 40초가 걸려 1분 목표를 넘습니다. Java 묶음 판정에서는 경고가 많으면 `VerdictBatch`가 제한 시간까지 심각도 순서로 판정하고, 나머지는 판정 불가로 남깁니다. 이 경우 1분은 지키지만 그 경고들의 오탐은 줄지 않습니다.

### 수정안 (진짜 취약점 예제 21건)

- **사전 검사 통과:** 20/21. CWE별 수정 방법을 프롬프트에 넣기 전에는 19/21이었지만, 고쳐지지 않은 코드가 많았습니다.
- **코드를 직접 읽은 결과:** 약 16건이 제대로 고쳐진 것으로 보입니다. 사람이 읽고 판단한 값이며, 컴파일과 재분석은 하지 않았습니다.
- **발견한 문제:** `sizeof(out)`을 포인터에 사용, `unsigned int` 덧셈을 `SIZE_MAX`로 검사, 위험 코드를 실행되지 않게 만든 수정, 사용자 입력을 기준 폴더로 쓴 경로 검사.
- **목표와의 관계:** 재검증 통과율 70%는 S7을 연결해야 측정할 수 있습니다.

### 모델 비교 (v0.2.0 기준, 예제 8건)

| 모델 | 정답 | 판정 1건 중앙값 |
|---|---|---|
| `qwen2.5-coder:7b` | 7/8 | 34.1초 |
| `qwen2.5-coder:3b` | 5/8 | 6.1초 |
| `exaone3.5:7.8b` | 4/8 | 45.6초 |

정확도를 우선해 7B를 선택했습니다. 시간은 2단계 판정을 넣기 전 값입니다.

**리얼타임 질문에 답할 근거:** 판정 1건이 약 8초라 키 입력마다 판정하는 방식은 이 하드웨어에서 어렵습니다. 저장할 때 바뀐 함수만 다시 판정하는 방식은 `judgeFacts`로 시도해 볼 수 있지만, 만들어 검증하지는 않았습니다.

## 5. 한계

- 재검증 통과가 코드의 완전한 안전을 보장하지 않습니다.
- LLM이 낸 `confidence`는 실제 정확도와 맞지 않을 수 있어 화면에 표시하지 않습니다.
- 정적 분석이 놓친 취약점은 LLM도 찾지 못합니다.
- 인젝션 방어 4/4는 소수의 예제 결과이며 완전한 방어가 아닙니다.
- C 함수 추출은 전처리 분기로 중괄호 짝이 어긋나거나 `extern "C"` 블록 안에 있으면 ±30줄로 대체됩니다.
- 측정 PC 기준이며, GPU가 다르면 시간이 달라집니다.
